You describe it. Claude types it. A step-by-step way in, for people who have never written code this way, or at all.

Start at step 1 Or hand this page to your Claude

Before anythingThe idea

Coding with Claude is a conversation with three moves. You already know how to do all three.

1 Ask

Say what you want to see

Not how to build it. “A plot of response against contrast, one line per condition.” The way you’d ask a new postdoc.

2 Look

Look at what came back

Open the page. Read the figure. Check the numbers. You are the one who knows whether it’s right.

3 Steer

Say what’s off

“The axis should be log.” “Subject 4 looks wrong, why?” Then round again. Most of the work is this third move.

Think: a fast new postdocClaude is like a very quick, very well-read postdoc sitting at your keyboard. It types, runs things, reads the errors, and fixes them. It doesn’t know your science or your data until you tell it, and it can be confidently wrong. So you stay the PI: you set the question and you check the answer.
You don’t learn the tools firstGit, the terminal, the cluster’s job system: you learn those the way you learned the copier, by needing them once with someone beside you. Here that someone is Claude. Every confusing step below is a thing you can ask it to do, and to explain as it goes.

Step 1 · ten minutesSet up

You need a computer and a paid Claude plan (Pro, Max, Team or Enterprise). Nothing else. No coding tools to install first.

  1. Get the Claude desktop app

    Download it for Mac or Windows from the desktop quickstart, open it, and sign in.

  2. Click the Code tab

    It’s at the top of the sidebar. Chat is where Claude talks. Code is where Claude can also do: make files, run them, fix them. That’s the whole difference.

  3. Give it a folder

    Make an empty folder somewhere easy, like Documents/vibin-practice. Under the prompt box, pick Local, then Open folder…, and choose it. Claude works inside this folder. Think of it as the bench you’ve cleared for it.

  4. Leave it asking permission

    Also under the prompt box is a mode switch. Start on Manual: Claude asks before it changes a file or runs a command. Read what it asks and say yes. It’s the fastest way to learn what’s going on. When the asking gets tedious, switch to Accept edits.

I’d rather use the terminal

Same Claude, in a terminal window. On a Mac, open Terminal and paste:

curl -fsSL https://claude.ai/install.sh | bash

On Windows, in PowerShell: irm https://claude.ai/install.ps1 | iex. Then open a new terminal window, go to your folder, and start it:

mkdir -p ~/Documents/vibin-practice
cd ~/Documents/vibin-practice
claude

It asks you to sign in the first time. Everything below works the same way.

You now haveClaude, looking at an empty folder, waiting.

Step 2 · five minutesFirst demo

Make something you can see. One file, opens in a browser, nothing to install.

Make me a single web page called gabor.html that shows a Gabor patch on a gray background, with sliders for contrast, spatial frequency, orientation and size. No libraries, just the one file. Then open it in my browser.

Say yes when it asks. A minute later you have something like this. It’s live, so move the sliders:

Now change it. Pick one, or make up your own:

  • Make it drift, and add a slider for speed.
  • Add a second patch next to it. Let me press the left or right arrow to say which one has higher contrast, and keep score.
  • The sliders are too small. Make everything bigger and easier to read.
Not a vision person?Swap the first prompt for anything you can picture: a Stroop task, a reaction-time game, a calculator for your grant budget. The rule is only that it’s one page you can look at.

You now haveA working thing you made by describing it, and changed by describing it again.

Step 3 · a habit, not a taskThe loop

Ask, look, steer. You just did it. These make it go better.

  • Describe the resultSay what you want to see or get, and how you’d know it’s right. Leave the how to Claude.
  • Give it what you’d give a studentThe file, the paper’s method, an example of the figure you like. Context is most of the quality.
  • Paste the messWhen something breaks, paste the error or say exactly what you see. Don’t tidy it up or guess the cause.
  • Small bitesOne change, look, next change. Ten small rounds beat one giant request.
  • Ask whyYou’re allowed to not understand. Ask, every time. It never gets tired of it.
  • Start fresh when it’s muddledA long conversation gets foggy. Open a new session and say where things stand.

Three to keep in your pocket

  • Explain what you just built, like I’m a new grad student. Which file does what?
  • Before you build anything, tell me your plan in five lines and wait for my OK.
  • That’s not right. Here’s what I see: [describe it, or paste the error]. What are the likely causes? Check them before changing anything.

You now haveThe whole method. Everything after this is the same loop pointed at bigger things.

Step 4 · ten minutesSave points

Git, without learning git.

Git is save points in a video game. Before the boss fight you save. If it goes badly, you go back. Each save has a note saying what you’d just done, so the saves are also a lab notebook that writes itself. Git has a reputation because its commands are strange. You won’t be typing them.

I’ve never used git. Set it up for this folder: check that git is installed (help me install it if it isn’t), set my name and email, and save a first checkpoint. Tell me in one sentence what each thing you do is for.

From then on, this is all of git you need to say:

  • Save a checkpoint.
  • What’s changed since the last checkpoint?
  • I don’t like where this went. Take me back to the last checkpoint.
  • Show me the history as a short list.
The habitSave a checkpoint whenever something works, and before you ask for anything big. Then nothing Claude does can cost you more than a few minutes.

You now haveAn undo button for the whole folder, and a record of what you did.

Step 5 · fifteen minutesPut it online

A link you can send to a colleague.

GitHub is where the save points live when they’re not on your laptop. A copy off-site, like Dropbox for the notebook. It can also show a web page to the world, for free. That part is called Pages.

  1. Make a GitHub account

    Go to github.com/signup. This one is yours to do: it’s your name and your password.

  2. Let Claude do the rest 
    I have a GitHub account, username [yours]. Connect this computer to it: install the GitHub command-line tool (gh) if it’s missing and walk me through signing in. I’ll do the browser part myself. Then make a new public repo called gabor-demo from this folder, push it, and turn on GitHub Pages so I get a link I can send to someone. Rename gabor.html to index.html if the link needs that.

    At one point it hands you a short code to type into a GitHub page in your browser. That’s you proving it’s you. After that it won’t ask again.

  3. Send the link to someone

    It looks like https://yourname.github.io/gabor-demo/ and takes a minute or two to appear the first time. From now on “save a checkpoint and push it” updates the page.

Public means publicAnyone can read a public repo. Demos and code: fine. Data, never. For work that isn’t ready, ask for a private repo instead.

You now haveYour demo on the internet, and your work backed up somewhere that isn’t your laptop.

Step 6 · twenty minutesYour own data

On your laptop first. Something small: a spreadsheet, a CSV, one subject’s behavior.

  1. Put a copy in the folder

    Make a data folder inside your practice folder and drop a copy of a file in it. Nothing with names or birth dates in it. No data handy? Skip to the note below.

  2. Have Claude look before it touches 
    There’s a file in data/. Don’t change it. Look at it and tell me what’s in it: the columns, how many rows, and anything odd, like missing values or ranges that don’t make sense. Then stop.

    Read what it says. This is where you catch that column 3 is in milliseconds, not seconds.

  3. Ask for a script, not an answer 
    Write a Python script that reads that file and plots [what you want: say, mean response for each condition, with error bars across subjects]. Save the figure in figures/. Print the numbers behind the figure so I can check them. Then run it and show me the figure.

    A script is a recipe card: anyone can run it again and get the same figure. An answer in the chat is a meal you can’t remake.

  4. Check it like a reviewer 
    What assumptions did you make in that analysis? List them. Then tell me one way I could check the result by hand.
  5. Save a checkpoint

    You know how.

No data handy?The kit has a practice set. Say: “Download https://linglab.org/vibin/vibin-kit.zip, unzip it here, and run make_toy_data.py.” You get eight made-up subjects: responses at seven contrasts, attended and unattended.

You now haveA figure from your own data, the script that makes it, and both saved.

Step 7 · fifteen minutesThe SCC door

For people with an account on BU’s Shared Computing Cluster. No account? A faculty member starts a project, or the lead of an existing one adds you: see Accessing the SCC.

Your laptop is your office. The SCC is the big shared workshop across the state (it really is: the machines are in Holyoke). You don’t move in. You send work orders and get results back. Claude stays on your laptop and reaches the workshop through a door that you open.

The door is a secure connection called SSH. Normally every trip through it means your password and a Duo tap. The trick is to badge in once and prop the door open, so everything after that walks straight through.

  1. Have Claude build the door 
    I have an account on BU’s SCC. My login name is [yours]. Set up the file ~/.ssh/config on this computer so that “ssh scc” connects to scc1.bu.edu and keeps one shared connection open for 12 hours (ControlMaster), so I only log in once a day. Back up my existing config first. Don’t try to log in for me: tell me the one command to run, and I’ll type my password and approve Duo myself.
  2. Open it yourself

    In the desktop app, open the terminal pane (Ctrl+`), or use the Terminal app. Type this, then your BU password, then approve Duo on your phone:

    ssh -fN scc

    Nothing visible happens. That’s success: the door is open and stays open. Do this once each morning you want to use the cluster.

  3. Have Claude look around 
    Check that my SCC connection is open (ssh -O check scc). Then look around, read-only: where is my home directory, which projects am I in, where is my project space, and how full is it? Change nothing.
  4. Write down the rules 
    Download https://linglab.org/vibin/kit/CLAUDE-starter.md. Fill in what you just learned about my SCC setup, ask me about anything you can’t work out, and save it as CLAUDE.md in this folder.

    Claude reads CLAUDE.md every time it starts in this folder. It’s the note taped above the bench: ask before submitting jobs, never delete, never touch my password. Read the starter and change it to suit you.

Two things Claude never doesType your password, or approve Duo. If it ever seems to need either, the door has closed: open it again yourself.
On Windows

The prop-the-door-open trick needs Mac or Linux. On Windows, do this step inside WSL (the Linux that comes with Windows). Tell Claude you’re on Windows and ask it to set that up with you.

You now haveClaude able to see your cluster files, on a connection you opened and can close.

Step 8 · ten minutesA first job

Send one small work order and watch it come back.

When you log in to the SCC you’re at the front desk (the login node): fine for looking around and dropping off orders, not for running the machines. Real work goes in as a batch job: a short script that says what to run and how much time it needs. You hand it to the scheduler with qsub, it waits in line, runs on a machine in the back, and leaves its output in a file.

Download https://linglab.org/vibin/kit/hello.qsub. Put it in a new folder called vibin-practice in my project space on the SCC, fill in my project name, and submit it. Watch the queue until it finishes, then show me what it printed. Explain qsub, qstat and the output file in one sentence each.

Since your ground rules say to ask before submitting, it will ask. Say yes. You get back a line like Hello from scc-xx1 at Tue Nov 24…: a machine you’ve never seen, saying hi.

You now haveThe full round trip: laptop to cluster to laptop. Every analysis from here is this, with a bigger script.

Step 9 · thirty minutesA whole analysis

A rehearsal on made-up data, where the right answer is known. Same shape as the real thing: one subject, check, everyone, gather.

The kit’s practice set is eight invented subjects with a contrast response function that attention shifts to the left. Because the data are invented, the truth is on file, and you can see whether the analysis finds it. It’s the fire drill before the fire.

  1. Set the table 
    Download https://linglab.org/vibin/vibin-kit.zip and unzip it here. Read the three Python files and the two .qsub files and tell me in plain words what each one does. Then copy them to my vibin-practice folder on the SCC and run make_toy_data.py there.
  2. One subject first 
    Fill in my project name in analysis.qsub. Submit it for the first subject only, as a test. When it’s done, show me the log and the fitted values. Do they look sensible for a contrast response function?

    The oldest rule of cluster work: never send two hundred jobs to find out they all crash on line 3.

  3. Then everyone 
    That looks right. Submit all the subjects as an array job. Tell me when they’ve finished and whether any failed. If one failed, read its log and tell me why before you fix anything.

    An array job is one work order for the same thing, eight times, side by side. Eight subjects take as long as one.

  4. Gather, and bring back only the small stuff 
    Fill in my project name in summarize.qsub and submit it. When it’s done, copy just the summary table and the figure back here, into results/ and figures/. Show me the figure and read me the known-answer check.

    You should see two curves, the attended one shifted left, and a line saying how close the fits came to the truth.

  5. Save a checkpoint

    The scripts live in your folder and in git. The cluster holds a working copy and the heavy data. If the cluster copy vanished tomorrow, you’d lose nothing you couldn’t rerun.

You now haveA complete, repeatable cluster analysis, start to figure. Mostly by saying “yes” and “show me”.

Step 10 · the point of all thisYour question

Now your data, where it already lives. Same four beats, and one new one at the front: Claude learns the lay of the land before it does anything.

First, the data questionWhat Claude reads passes through Anthropic’s servers, like any cloud service. De-identified derivatives are usually fine. Check your IRB protocol and BU’s guidance before it reads anything that could identify a participant, and say so in your CLAUDE.md.
  1. Survey 
    My data for [study] is on the SCC at [/projectnb/yourproject/…]. Survey it, read-only: the folder structure, how many subjects, the file types and sizes, and anything that’s inconsistent across subjects. Don’t copy data to this computer. Write what you find to notes/data-map.md here, and add the short version to CLAUDE.md.

    Correct the map where it’s wrong. You do this once; after that Claude knows where things are.

  2. Plan 
    Here’s the analysis I want, in plain words: [for each subject, do this… then across subjects, compare that…]. Don’t write code yet. Give me a plan: which scripts, which jobs, roughly how long and how much memory, and where the outputs go. Tell me what you’re unsure about. Wait for my OK.
  3. One subject 
    OK. Do one subject. Show me its output and a quick picture of it, then stop.

    Look hard here. This is the cheapest moment to be picky.

  4. Prove it on a known answer 
    Before we run everyone: simulate data where we know the true answer, run this same analysis on it, and show me that it recovers the truth. If it doesn’t, say so plainly.
  5. Everyone, then gather 
    Run all subjects as an array job. When it’s done: which failed and why, then the group figure and the table behind it, copied back here. Save a checkpoint.

You now haveYour own analysis, on your own data, on the cluster, in a form you can rerun and hand to a student.

Worth taping to the wallHouse rules

How to stay the scientist while something else does the typing.

  • You check the answerClaude is fast and fluent and sometimes wrong. A figure isn’t a finding until you’ve looked at the numbers behind it.
  • Known answers firstBefore trusting an analysis on real data, run it on data where you know the truth.
  • One, then manyOne subject, look, then everyone. On your laptop and on the cluster.
  • Originals are read-onlyWork on copies. Write outputs somewhere new. Ask before anything is deleted or overwritten.
  • Passwords are yoursNever paste a password or a Duo code into Claude. You open the doors; it walks through.
  • Nothing identifyingNo names, birth dates or raw headers in what Claude reads, in git, or online.
  • Save before big asksA checkpoint costs two seconds and makes every experiment free.
  • A second pair of eyesFor anything that matters, open a fresh session and say: “Review this analysis for mistakes. Assume there is one.”

It will happenWhen stuck

Being stuck is normal, and it’s usually one message from being unstuck.

What you seeWhat to do
An error, any errorPaste it to Claude as it is. That’s the whole move. Errors are for it to read, not you.
It’s going in circlesSay “stop, go back to the last checkpoint”, then describe what you want differently, or smaller.
It did too much“Undo that. Next time, tell me the plan first and wait.” Add that line to CLAUDE.md and it sticks.
You don’t understand a wordAsk. “What’s a branch, in one sentence, with an analogy?”
“SCC connection closed”The door shut (overnight, or the laptop slept). Run ssh -fN scc again.
A job sits at qwIt’s waiting in line. Normal. Ask Claude to check again in a few minutes.
A job vanished with no result“Find the log for that job and tell me why it stopped.” Usually it ran out of time or memory; ask for more of whichever.
Something about the cluster itselfThe SCC’s people are helpful and fast: help@scc.bu.edu. Have Claude draft the email with the job number in it.

Fifteen of themWords

The jargon, each in a sentence. You don’t need to memorize any of it.

Terminal
A window where you type commands instead of clicking. Claude types there for you.
Repo
A project folder that remembers its own history. Short for repository.
Git
The thing that keeps the history. Save points.
Commit
One save point, with a note. “Checkpoint” in this guide.
GitHub
A website that keeps a copy of your repo off your laptop.
Push / pull
Send your save points up to GitHub / bring the latest down.
Branch
A parallel draft, so you can try something without touching the good copy.
Pages
GitHub showing a repo as a website.
Script
A file of instructions the computer can rerun. The recipe card.
SSH
A secure line from your computer to another one. The door.
Login node
The cluster’s front desk. Look around, drop off work, don’t compute.
Batch job
A work order for the cluster: what to run, how long, how big.
qsub / qstat
Hand in a work order / see where it is in line.
Array job
One work order run many times at once, say once per subject.
Module
Software already installed on the cluster. module load python3 switches it on.
